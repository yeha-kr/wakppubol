# 왁뿌볼 만들기 게임 — 설계 계획서

- 문서 버전: v1.0 (2026-07-29)
- 용도: Claude Code 개발의 기준 문서. 프로젝트 루트에 `docs/PLAN.md`로 저장해 두고 매 세션에서 참조시킨다.

---

## 0. 요약

플래시 쿠킹 게임 감성의 "왁뿌볼 제작 + ASMR 파괴" 모바일 웹 게임. 4단계(점토 반죽 → 왁스 코팅 → 고무·케이블타이 → 부수기)로 진행하며, 게임의 성패는 마지막 파괴 단계의 소리 품질에 달려 있다.

핵심 결정 3가지:

1. Flash는 2020년 말 지원 종료로 모바일에서 실행 자체가 불가능 → HTML5(Phaser 3)로 구현
2. Stage 4(부수기 + 사운드)를 가장 먼저 프로토타입 — 핵심 재미 검증을 가장 싸게, 가장 빨리
3. 개발자 정보의 캡처 "완전 차단"은 기술적으로 불가능 → 억제책 + 게시 정보 최소화로 접근 (8장 필독)

## 2. "플래시 게임"의 해석

Adobe Flash Player는 2020-12-31에 지원이 종료되었고, 현재 모바일 브라우저에서는 실행되지 않는다. 따라서 "플래시 게임"은 그 시절 쿠킹 게임의 스타일(단계별 미니게임, 과장된 효과음, 귀여운 2D 그래픽)을 뜻하는 것으로 해석하고, 구현은 HTML5로 한다. 링크 하나로 폰에서 바로 실행되므로 배포는 오히려 더 쉽다.

## 3. 기술 스택과 선정 근거

| 영역 | 선택 | 근거 |
|---|---|---|
| 게임 엔진 | Phaser 3 (3.8x) | 씬 관리·터치 입력·트윈·파티클·에셋 로더·사운드가 전부 내장 → 씬 전환형 미니게임 구조에 정확히 맞음. 자료·예제가 많아 Claude Code가 정확한 코드를 생성할 확률이 높음. 대안인 바닐라 Canvas는 의존성이 없지만 위 기능을 전부 직접 구현해야 해서 개발량과 버그 표면적이 커짐 |
| 빌드 | Vite + JavaScript | 설정이 최소이고, 개발 서버를 `--host`로 띄우면 같은 와이파이의 폰에서 즉시 테스트 가능. TypeScript는 이 규모에서 이점보다 진입 비용이 큼 |
| 오디오 | Web Audio API (Phaser Sound Manager) | 터치→발음 지연 최소화에는 사전 디코딩된 AudioBuffer 재생이 필수. `<audio>` 태그는 모바일에서 지연·동시 재생 제한 문제가 있음. iOS는 사용자 제스처 이전 재생을 금지하므로 "탭하여 시작"에서 AudioContext를 resume한다 |
| 사운드 포맷 | mp3, 44.1kHz | Safari가 ogg를 지원하지 않으므로 mp3 단일 포맷이 가장 단순한 전 브라우저 호환안 |
| 햅틱 | navigator.vibrate | Android Chrome만 지원. iOS 웹은 진동 API 자체가 없음 → iOS는 사운드와 화면 흔들림으로 보완해야 하는, 수용할 수밖에 없는 한계 |
| 배포 | GitHub Pages 또는 Vercel | 정적 파일뿐이라 무료·간단하고 HTTPS 기본 제공(일부 API는 HTTPS 필수) |

└─ src/
   ├─ main.js

## 5. 씬 흐름

Boot → Preload("탭하여 시작" = 오디오 언락) → Title → Stage1 → Stage2 → Stage3 → Stage4 → Result. Credits(개발자 정보)는 Title/Result에서 진입.

씬 간 데이터(선택한 점토 색, 코팅 레이어 수, 시작 시각)는 Phaser registry로 전달한다.

## 6. 스테이지 상세

### Stage 1 — 점토 떼서 섞어 뭉치기

- 조작: ① 하단 점토 3색 중 원하는 덩이를 잡고 위로 드래그, 약 100px을 넘기면 조각이 "뜯어짐"(늘어났다 끊기는 스케일 트윈 + 뜯기 효과음) ② 중앙 볼에 2~3조각 담기 ③ 볼 위를 원 그리듯 문지르기 → 누적 이동거리에 비례해 게이지 상승 (단순 탭으로는 게이지가 오르면 안 됨)
- 혼합 표현: 게이지 25/50/75/100% 구간마다 혼합 단계 스프라이트 교체. 실시간 색 블렌딩 셰이더는 모바일 성능·개발 난이도 대비 이득이 없어 배제
- 완료: 100% → 공으로 뭉쳐지는 트윈 → 선택 색을 registry에 저장 → Stage 2
- 사운드: 뜯기 3종 랜덤, 반죽 루프(문지르는 속도에 볼륨 연동)

### Stage 2 — 왁스에 담갔다 빼기

- 조작: 공을 드래그해 냄비에 담금 → 1초 유지 → 위로 빼기
- 판정: 빼는 순간 속도가 임계값(초안 800px/s, 실기기 튜닝) 초과면 "얼룩 실패" → 해당 레이어 무효, 재시도. 쿠킹 게임식 타이밍 요소
- 반복: 성공 4회로 코팅 완성. 레이어마다 공 스프라이트 교체(점점 매끈하고 광택)
- 연출·사운드: 담글 때 첨벙, 뺄 때 왁스 방울 파티클 + 드립 소리

### Stage 3 — 고무 패팅 + 케이블 타이

- 해석 주의: "고무 패팅"은 고무 시트를 두드려 감싸는 공정으로 설계했다. 실제 의도가 다르면(예: 풍선·고무막 씌우기) 이 스테이지의 인터랙션만 교체하면 되도록 독립 구성한다
- 조작: ① 공 표면 8구역을 탭 → 탭한 구역이 고무로 덮임("팟" 소리), 8/8 완료 시 다음 ② 케이블 타이가 걸린 상태에서 아래로 길게 스와이프 → 당길수록 래칫 "틱" 간격이 좁아지고, 끝까지 당기면 "지익" 조임 + 공이 살짝 눌리는 스퀴시 연출
- 사운드: 고무 팟팟 3종, 래칫 틱, 조임 지익

### Stage 4 — 왁뿌볼 부수기 (핵심)

- 조작: 탭 = 작은 크랙 / 빠른 연타 = 중간 크랙 / 길게 눌렀다 떼기(300ms+) = 큰 크랙(데미지 3배)
- 파괴 모델: 껍질을 12구역으로 나눠 구역별 데미지 누적. 임계 초과 구역은 파편 스프라이트로 분리되어 중력 낙하 + 회전. 전 구역 분리 시 속 점토 공 노출 → 클로즈업 → Result
- 크랙 표현: 터치 지점에 크랙 데칼(5종, 랜덤 회전·스케일 0.8~1.2) 오버레이. 실시간 Voronoi 분할이나 물리엔진(Matter.js) 도입은 배제 — 근거: 모바일 저사양에서 프레임 저하 위험이 크고, "데칼 + 조각 낙하" 방식으로도 체감 품질이 충분하다는 것이 모바일 캐주얼의 검증된 패턴
- 완파 연출: 큰 파열음 1회 + 파편 낙하음 3~5개를 30~80ms 랜덤 간격으로 겹쳐 "와르르" 질감

## 7. 사운드 설계 (프로젝트 최우선 순위)

### 7.1 원칙

- BGM은 없거나 극히 작게 둔다. 이 게임의 가치가 크랙 사운드의 디테일이므로 그것을 가리는 요소를 두지 않는다
- 모든 SFX는 Preload에서 사전 디코딩 → 터치 후 50ms 이내 발음을 목표

### 7.2 크랙 사운드 사양

| 계층 | 용도 | 변형 수(최소~권장) |
|---|---|---|
| crack_small | 탭 미세 크랙 "짝" | 3~5 |
| crack_mid | 연타 "짜자작" | 2~4 |
| crack_big | 홀드 릴리즈, 구역 분리 "와작" | 2~3 |
| shard | 파편 낙하 "타닥" | 2~3 |

- 재생 규칙: 같은 샘플 연속 금지(라운드로빈) + playbackRate ±10% + 볼륨 ±20% 랜덤. 근거: 단일 샘플의 반복 재생은 즉시 인공적으로 들린다 — "샘플 풀 + 피치 랜덤"은 게임 오디오의 표준 기법
- 파괴 진행도가 높아질수록 big 비중을 늘려, 껍질이 약해질수록 굵은 크랙이 나는 실제 질감을 모사

### 7.3 사운드 소스 확보 (우선순위)

1. 직접 녹음(강력 권장): 실제 왁뿌볼, 없으면 대체물(템퍼링한 초콜릿 셸, 얇은 양초 껍질)을 조용한 방에서 폰 마이크 5~10cm 근접 녹음. 가장 진짜같고 라이선스 문제가 0
2. 무료 라이브러리: freesound.org에서 라이선스를 CC0로 필터해 "wax crack", "thin ice crack", "chocolate shell snap" 검색. CC-BY 샘플은 크레딧 표기 의무가 있으므로 라이선스를 반드시 확인
3. AI SFX 생성(ElevenLabs SFX 등): 프롬프트는 「프롬프트 모음」 문서 참조
- 금지: 유튜브 ASMR 영상에서 소리 추출 — 저작권 침해

### 7.4 편집 규격

각 샘플 앞 무음 제거(어택 즉발), 길이 0.1~0.6초, 피크 -1dB 노멀라이즈, 모노, mp3 44.1kHz.

## 8. 개발자 정보(Credits) 페이지 — 필독

### 8.1 표시 내용

사진 / "성균관대학교 전자전기공학부 2학년 신예하" / 이메일 / 재학 인증

### 8.2 먼저 알아야 할 한계 (솔직 고지)

"캡처·다운로드가 안 되게"는 절대적인 의미로는 구현 불가능하다.

- 스크린샷은 OS 기능이다. 브라우저 안의 웹페이지는 OS 스크린샷을 감지하거나 막을 권한이 없다
- 넷플릭스 캡처가 검게 나오는 것은 DRM(EME)으로 보호되는 동영상 스트림 전용 메커니즘이며, 일반 이미지·웹페이지에는 적용할 수 없다
- 무엇을 하든 다른 기기로 화면을 촬영하는 것은 막을 수 없다

따라서 목표를 "차단"이 아니라 ① 저장·수집을 귀찮게 만들기(억제) ② 유출되어도 피해가 없게 만들기(정보 최소화), 두 가지로 잡는다.

### 8.3 적용할 억제책

- 사진·증명서를 DOM `<img>`가 아닌 캔버스 텍스처로만 렌더 → 롱프레스 "이미지 저장", 이미지 주소 복사 차단
- contextmenu 이벤트 차단, `user-select: none`, `-webkit-touch-callout: none`
- 화면 전체에 반투명 대각선 워터마크("확인용 · 날짜") 반복 오버레이
- 탭 이탈(visibilitychange) 시 블러 처리
- 이메일: mailto 링크 없이, 문자열을 코드에서 조각으로 나눠 런타임 조립(크롤링 봇의 스팸 수집 억제)

단, 위 전부는 개발자도구 등으로 우회 가능하다. 그래서 8.4가 실질 대책이다.

### 8.4 실질 대책 (강력 권고)

- 재학증명서 원본을 공개 웹에 올리지 말 것. 증명서에는 학번·생년월일(양식에 따라 주민번호 일부)·발급번호가 있고, 이는 사칭·명의도용에 쓰일 수 있는 실질적 위험이다
- 올린다면: 이름·학교·학부만 남기고 나머지를 전부 마스킹한 사본을, 낮은 해상도(가로 400px 이하) + 워터마크로
- 더 권장: 증명서 이미지 대신 "성균관대학교 전자전기공학부 재학 인증 ✓" 배지 + 텍스트로 대체
- 사진도 원본 해상도가 아니라 표시 크기에 맞춘 저해상도만 사용

## 10. AI 이미지 제작 워크플로

- 최대 리스크는 에셋 간 스타일 불일치다. 대응: 모든 프롬프트에 동일한 스타일 서픽스를 고정하고, 가능한 한 같은 세션에서 연속 생성하며, 잘 나온 1장을 레퍼런스로 첨부해 후속 생성
- 투명 배경: 생성 모델이 투명 PNG를 제대로 못 만들거나 체커보드 무늬를 그림으로 그려버리는 경우가 흔하다 → 순수 마젠타(#FF00FF) 단색 배경으로 생성한 뒤 배경 제거 도구(remove.bg, Photopea 등)로 후처리
- 한글 텍스트(로고 등)는 생성 모델이 자주 깨뜨린다 → 로고 글자는 무료 한글 웹폰트(주아, 검은고딕 등)로 코드에서 렌더하고, 이미지는 마스코트·장식만 생성

## 11. 개발 로드맵

| 단계 | 내용 | 완료 기준 |
|---|---|---|
| M0 | 셋업, 씬 골격, 오디오 언락 | 폰에서 씬 순회 |
| M1 | Stage 4 프로토타입(임시 그래픽·임시 사운드) | 폰에서 부수기+사운드 재미 검증 |
| M2 | Stage 1 → 2 → 3 | 각 스테이지 플레이 가능 |
| M3 | 타이틀·결과·흐름 연결 | 처음~끝 1회 플레이 |
| M4 | 개발자 정보 페이지 | 억제책 포함 동작 |
| M5 | 실에셋·실사운드 교체, 폴리시 | 튜토리얼·햅틱·음소거 |
| M6 | 실기기 테스트, 배포 | 공개 URL |

M1을 앞에 두는 이유: 이 게임 가치의 대부분이 파괴+사운드에 있다. 여기가 재미없으면 방향을 바꿔야 하므로 가장 싼 형태(임시 그래픽)로 가장 먼저 검증한다(fail fast).

## 12. 테스트 체크리스트 (실기기 필수)

- iOS Safari: 첫 탭 후 소리 재생 여부, 무음 스위치 상태에서의 동작 확인, 홈바 스와이프 오작동 없음
- Android Chrome: 진동 동작, 터치 반응 속도
- 공통: 터치→소리 지연 체감, 연타 중 55fps 이상, 세로 고정, 화면 확대·스크롤 바운스 없음(touch-action: none), 저사양 기기 1대 포함
- 데스크톱 크롬의 모바일 에뮬레이션은 오디오 지연·터치 감도가 실기기와 달라 최종 판정에는 쓰지 않는다
